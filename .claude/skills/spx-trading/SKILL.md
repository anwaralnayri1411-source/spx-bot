# سكيل التداول: مشروع «عين السوق»

بوتات إشارات فقط (لا تنفّذ صفقات) تعمل على GitHub Actions وترسل إلى تيليجرام. المستخدم سعودي يستخدم الآيفون ولا يملك وسيط تداول.
أجب بالعربية، باختصار، والمبالغ بالدولار، والروابط في سطر مستقل.

## 0) قبل أي شيء
1. جهّز نسخة حديثة من المستودع:
   - في بيئة سحابية: المستودع هو مجلد العمل، فقط `git pull --rebase`.
   - على جهاز المستخدم (ويندوز): استنسخ في مسار قصير لأن المسارات الطويلة تفشل:
     `C:\Users\sa\AppData\Local\Temp\spxbot\repo` (إن وُجد فـ `git pull --rebase`).
2. اقرأ `CLAUDE.md` ثم `HANDOFF.md`. فيهما القواعد الإلزامية وآخر النتائج والأمور المعلّقة، وهما المرجع إذا تعارضا مع هذا الملف.
3. على جهاز المستخدم: Python في `C:\Users\sa\AppData\Local\Python\bin\python.exe` (فيه pandas وyfinance، وليس فيه playwright ولا pyyaml). الرفع يعمل بـ `git push`، و`gh` غير مثبّت؛ تحقق من التشغيلات عبر الواجهة العامة:
   `https://api.github.com/repos/anwaralnayri1411-source/spx-bot/actions/workflows/<file>.yml/runs`

## 1) قواعد ثابتة (مختصرة من CLAUDE.md)
- بوت SPX وبوت الشركات مشروعان منفصلان؛ لا تخلط منطقهما.
- اسأل قبل لمس الملفات المشتركة: دوال الإرسال في `options_bot.py` و`cards.py` و`commands_bot.py`.
- لا تغيّر منطق التوصيات إلا بعد اختبار وموافقة صريحة. أي فكرة جديدة تبدأ «في الظل» (تسجيل فقط).
- التجارب الجديدة تُرسل إلى `TELEGRAM_CHAT_ID` وحده، لا إلى `TELEGRAM_EXTRA_CHAT_IDS`، حتى يوافق المستخدم.
- فضّل ملفات جديدة على تعديل القديمة، ولكل سير عمل جديد `concurrency group` خاص به.
- `git add a b` لا يضيف شيئاً إن غاب أحد المسارات: أضف كل ملف وحده.
- لا تحذف ملفات أو سجلات دون إذن. لا يلصق المستخدم مفاتيح في المحادثة: الأسرار في GitHub Secrets فقط.
- الصراحة دائماً: بيانات yfinance متأخرة ~15 دقيقة، أسعار العقود في المؤشرات نظرية، والعينات صغيرة.

## 2) مهمة: تحليل صورة أو تقرير محلل (مثل MGT)
لا تعدّل شيئاً أثناء التحليل. إذا قال المستخدم إنه سيرسل عدة صور، انتظر حتى يقول «انتهيت».
1. **النوع:** توصية دخول / متابعة عقد / تقرير بداية-منتصف-نهاية اليوم / قراءة سوق / شارت.
2. **استخرج كل رقم:** السعر، السترايك، الدخول، الهدف، الوقف، كل مستوى باسمه، الوقت (الرياض ونيويورك)، والمؤشرات (RSI/ADX…).
3. **استنتج المنهج:** على ماذا استند؟ (جدران العقود، انقلاب الجاما، ماكس بين، ATR، VWAP، أعلى/أدنى أمس، نطاق أول 30 دقيقة، اتفاق الفريمات، السيولة اللحظية، القياديات). ميّز «المؤكد» عن «المرجّح».
4. **قارن بما عندنا** في جدول: موجود ✅ / جزئي 🟡 / يحتاج بيانات لحظية ❌، مع اسم الملف.
5. **انتبه لطريقة حسابهم:** تقارير MGT تحسب الربح من القمة لا من الخروج، وتعدّ الصفقة رابحة إن بلغت +50$ حتى لو ضربت الوقف. لا تقارن أرقامهم بأرقامنا مباشرة.
6. **اقترح خطة** بتصميمنا الخاص (لا ننسخ شعارهم أو اسمهم)، تبدأ في الظل أو كتجربة للمستخدم وحده، ثم اسأل قبل البناء.
7. أرقام تقاريرهم تُسجَّل في `mgt_reports_log.csv` و`mgt_recs_log.csv`، لكن فقط بعد موافقة المستخدم.

## 3) مهمة: مراجعة النتائج
- المصادر: `zero_dte_log.csv` و`spx_positions.json` و`spx_track.csv` (SPX)، `stocks_log.csv` و`stocks_positions.json` و`stocks_track.csv` (الشركات)، سجلات الظل `shadow_*_log.csv` و`ladder_shadow_log.csv` و`spx_thesis_log.csv` و`gex_*.csv` و`signals_extra_log.csv`، و`research/*_results.md`.
- قاعدة الحكم (من CLAUDE.md): تعريف قابل للقياس ← اختبار 60 يوماً مقابل خط أساس عشوائي/وهمي ← ظل أسبوعين+ ← عرض الأرقام ← اعتماد ما تفوّق فقط.
- اعرض لكل فكرة: العدد، نسبة الهدف/الوقف، متوسط الربح بالدولار للعقد، والمقارنة بالعشوائي. قل صراحة «العينة صغيرة» إذا كان العدد أقل من 20.
- لا تقترح تغيير التوصيات من نتيجة واحدة أو أيام قليلة.

## 4) مهمة: قراءة السوق
- البطاقة في `market_read.py` و`market_read_card.py`، وسير العمل `market_read.yml` (يدوي، أو عند تعديل ملفاتها). تصل للمستخدم وحده.
- معاينة بلا إرسال: `python market_read.py --no-send --html preview.html` ثم اعرض الصفحة (Playwright غير مثبّت محلياً، فالصورة PNG تُرسم على GitHub فقط).
- عند الشرح بالعربية: الاتجاه ونقاطه، المقاومة والدعم اللحظيان، الوجهة المشروطة، متى يتغيّر التقييم، والتأكيد (الفريمات، RSI/ADX، الجاما). اختم بأنها قراءة وليست توصية.
- خارج الجلسة تكون الأرقام من آخر إغلاق، وأسعار السلّم لعقود الانتهاء القادم: قل ذلك.

## 5) قبل أي تعديل على الكود
1. اشرح ما ستغيّره وما لن يتأثر، واطلب الموافقة.
2. اختبر محلياً قدر الإمكان (بيانات حية عبر yfinance إن توفرت، أو `research/spx_5m_cache.csv`، أو بيانات وهمية).
3. التزامات صغيرة منفصلة، ثم `git pull --rebase` قبل `git push` (البوتات تلتزم باستمرار).
4. بعد الرفع تحقق أن سير العمل ظهر باسمه الصحيح وحالته active، وأن أول تشغيل نجح.
5. حدّث `HANDOFF.md` أو `CLAUDE.md` بسطر عن أي تغيير مهم، بعد موافقة المستخدم.
